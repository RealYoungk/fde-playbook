# 후속 서술형 대비

## 형식 (안내 기준, 회차마다 다를 수 있음)
- 제출물과 작업 기록을 바탕으로 문항이 생성된다
- AI 사용, 복사 붙여넣기 금지. 직접 타이핑
- 문항당 제한 시간이 짧고(수 분), 이전 문항으로 돌아갈 수 없다
- 확정 후에는 파일을 다시 볼 수 없을 수 있다. **확정 전에** 브리프를 읽어 둔다

## 답변 구조 (3단계, 250~400자)
1. **지점**: 내 코드의 구체적인 위치를 짚는다 (파일, 함수, 규칙, 숫자)
2. **파급**: 왜 위험하거나 중요한지, 누구에게 어떤 영향인지
3. **다음**: 어떻게 검증했거나 검증할지, 어떻게 개선할지
전제가 틀린 질문은 바로잡고, 구현하지 않은 기능을 물으면 현재 구조의 어디에 어떻게 넣을지로 답한다.

## 브리프 생성 지시
"제출물, DECISIONS.md, VERIFY.md, git log를 근거로 예상 문항 12개와 각 3단계 답 초안을 `docs/work/BRIEF.md`에 써줘. 답에는 실제 파일명, 함수명, 숫자를 넣어. 근거가 없는 내용은 쓰지 마."
그 다음 사람이 직접 읽고 틀린 곳을 고친다. 고치면서 이해 안 되는 부분이 있으면 그게 서술형에서 막힐 지점이다.

## 예상 문항 유형
| 유형 | 예 | 재료 |
|---|---|---|
| 설계 근거 | "왜 이 알고리즘/기준인가" | DECISIONS 결정 항목 |
| 트레이드오프 | "HR과 재무 관점 충돌을 어떻게 다뤘나" | 시나리오 비교표, AGREEMENT |
| 검증 | "AI 말만 믿지 않고 어떻게 확인했나" | VERIFY "실행자: 사람" |
| AI 활용 | "AI의 한계를 어떻게 다뤘나, 무엇을 거절했나" | AI 제안 기록, 오류와 수정 |
| 운영 장애 | "입력 파일이 잘못되면?", "동시에 수정하면?", "서버가 죽으면?" | 운영 리스크 표 |
| 구조 | "입력, 계산, 화면 책임을 어떻게 나눴나" | core / web_app 구조 |
| 한계 | "가장 불확실한 가정은? 틀리면?" | 가정 목록 |
| 확장 | "대상 건물이 늘면? 데이터가 10배면?" | 계산 복잡도, 구조 |
