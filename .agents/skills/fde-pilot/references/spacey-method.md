# 스페이스와이식 FDE 원칙 요약 (단계별 근거)

출처: 스페이스와이 황현태 대표 유튜브 '까칠한AI' 본편 19개, 인터뷰 기사, DIO 방법론 페이지. 상세 노트는 `../fde-discovery/references/kkachilhan-notes.md`. 학습용 그림 버전은 `docs/guide.html`.

## 흐름
타임박싱(3~6개월) → 원하는 것 먼저 빠르게 해서 신뢰 → 토폴로지 스캔 → 난제 정의 → "모레까지 눈으로" 빨간 펜 프로토 → 90% 데모와 Before/After → 성과 기반 KPI → 점진 배포(위험 낮은 팀부터, 병행) → 내재화, 메인테이너 남기고 떠남.
시험 180분 대응: P1 토폴로지(20분) / P2 합의(40분) / P3 v0와 빨간 펜(85분) / P4 종적 연결(130분) / P5 검토 / P6 인계.

## P1 토폴로지 스캔
- 고객은 셋: 시킨 사람, 책임지는 사람, 실제로 쓰는 사람. 여기에 숨은 결정권, 메인테이너.
- 우리를 가운데 두고 직접 소통 → 한 다리 건너 → 키맨 순서로 넓힌다. 사람 한 명이 DB이자 인터페이스.
- 질문: 누구에게 어떻게 칭찬받나, 실패하면 누가 리스크를 지나, 데이터가 없으면 누구에게 가나, 조직도에 없는 결정권자, 떠난 뒤 누가 유지하나, **왜 우리를 불렀나**.

## P1~P2 난제와 간극
- 내부 인원이 AI 돌려서 되는 일이면 우리가 필요 없다. "와, 이게 될까?"가 나와야 난제.
- 시험에서 README의 요구는 모두가 똑같이 구현한다. 점수 차는 README만으로 못 정하는 판단 하나에서 난다.
- 요구가 바뀌는 건 고객도 목표를 향해 가며 긴가민가하기 때문. 오너처럼 목표에 비춰 먼저 다음 안을 낸다.

## P1~P4 암묵지
- 현업은 당연한 걸 말하지 않는다. 예외, 관행, 작년 반응, 보고에 꼭 들어가는 숫자를 묻는다.
- 지식에는 화자와 상황을 붙인다. 같은 단어도 부서마다 뜻이 다르다.
- 충돌: 사실 오류 → 상황 차이 → 조직 문화("원래 어떻게 하셨어요?").

## P3 빨간 펜
- 요구사항 문서를 받아내려 하지 말고 돌아가는 화면에 빨간 펜을 긋게 한다. 예외와 승인 규칙도 화면을 보며 정한다.
- 우선순위 1~2개 흐름을 끝까지. Before/After 숫자로 만족도를 보이게.

## P4 종적 연결
- 업무를 옆으로 늘리면 아무도 체감 못 한다. 한 업무를 실무 → 보고 → 의사결정까지 위로 관통.
- 화면: 결론 한 줄(결정권자) / 기존안 비교(보고) / 실무 결과(현업).

## P6 버려질 준비
- 메인테이너를 정하고, 기준 바꾸는 법, 데이터 교체, 재계산 명령을 남긴다. "구축하고 나가면 녹슬 텐데"에 답하는 문서.

## 하지 말 것
- 업무마다 에이전트 하나씩 (유지보수 폭탄), 워크슬롭(검토 안 한 긴 AI 글), 몇 시간짜리 자동 루프(검수 불가), 바텀업 교육만, 납품형 구축 문법.

## 팔란티어 공개분
- Decomposition: 처음은 질문. 누가 쓰나, 몇 명이고 얼마나 기술적인가, 늦거나 틀리면 무엇이 깨지나.
- "완료" 정의를 설계보다 먼저. 너무 완전한 시스템을 그리지 않는다. 가장 작은 가치 단위를 먼저 배포.
- 온톨로지: 고객의 명사, 속성, 관계를 먼저 모델링(`ONTOLOGY.md`).
