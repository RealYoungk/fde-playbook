# FDE 조종석 (fde-pilot)

사용자는 현장에서 방법론을 떠올릴 여유가 없다. 이 스킬이 그 몫을 한다.
너는 매번 **지금 단계를 판단하고, 그 단계 일을 한 묶음만 하고, 아래 출력 형식으로 보고하고 멈춘다.**
담당자에게 직접 보내지 않는다. 사용자가 메시지를 읽고 고쳐서 보낸다.

원칙의 근거와 예시는 `references/spacey-method.md`, 메시지 틀은 `references/messages.md`, 답장 처리 규칙은 `references/reply-triage.md`.

## 상태 파일
`docs/work/PILOT.md` 하나로 진행을 기억한다. 없으면 만든다.
```
시작: 19:05   제출 시작: 21:55 (시작+170분)
현재 단계: P2
게이트: P1 ✅ 첫 메시지 보냄 19:22 / P2 ⏳ 합의 대기
담당자 대기 중인 질문: Q3, Q4
다음 할 일: 합의 메시지 발송 후 답장 붙여넣기
```
현재 시각은 `date +%H:%M`로 확인한다. 경과 시간과 남은 시간은 계산해서 쓴다. 추정하지 않는다.

## 명령
| 입력 | 할 일 |
|---|---|
| `시작 HH:MM` | PILOT.md 생성, P1 수행 |
| `다음` | 현재 단계 게이트를 확인. 통과면 다음 단계 수행, 아니면 빠진 것만 말하고 멈춤 |
| `답장` + 붙여넣은 글 | `references/reply-triage.md` 순서로 처리하고 회신 초안 |
| `상태` | PILOT.md 기준 시간, 단계, 게이트, 가장 큰 위험 하나 |
| `마무리` | 남은 기능 작업을 멈추고 P6로 바로 이동 |

시간이 단계 예산을 넘으면 "시간 초과"를 첫 줄에 쓰고, 그 단계에서 버릴 것을 제안한다. 100분에 제출 가능한 상태, 170분에 제출 시작은 깨지 않는다.

## 단계

### P1 조사와 토폴로지 스캔 (0~20분)
1. README, 과제 문서, 데이터 파일을 읽는다(큰 파일은 `head`, `wc -l`, 컬럼부터). `REQUIREMENTS.md`에 R1, R2... 조항으로.
2. 데이터 점검: 행 수, 결측, 중복, 이상치, 파일 간 키 불일치. 숫자는 코드로 계산.
3. `STAKEHOLDERS.md`: 문서와 데이터에 나온 사람, 부서를 전부 뽑아 시킨 사람 / 책임지는 사람 / 쓰는 사람 / 숨은 결정권 / 메인테이너 후보로 분류. 모르는 칸은 `?`.
4. 가설 두 개를 적는다. **왜 우리를 불렀나**(일손, 경험, 부서 간 이해관계, 시작점 중 무엇), **README만으로 못 정하는 간극** 후보 3개(누구에게 유리하게, 어떤 예외를, 어떤 숫자를 성공으로).
5. 첫 메시지: 이해한 것 2줄 + 질문 3~5개. 반드시 포함: 간극 질문 1개, 대리 질문 1~2개(최종 승인자, 다른 부서 관점, 운영할 사람), 암묵지 질문 1개(예외, 관행, 지난번 반응). 해결책 단어(AI, 자동화, 최적화) 금지. 선택형은 기본값을 붙인다.
- 게이트: 첫 메시지 발송(사용자가 "보냄"이라고 하거나 `답장`이 들어옴).

### P2 합의 (20~40분)
1. 답장을 반영해 목표, 제약, 숫자 성공 기준을 정리(`$objective-and-tradeoffs`). 임의 상수는 `$decision-cards`.
2. `AGREEMENT.md`: 문제 한 줄, 만들 것, 안 만들 것, 성공 숫자, 제약, 기본값으로 진행할 항목.
3. 합의 메시지: 위 내용을 6줄 이하로. "이대로 진행해도 될까요? 다르면 한 줄만 고쳐 주세요."
- 게이트: 담당자 확인 또는 무응답 10분(기본값으로 진행한다고 알리고 DECISIONS에 기록).

### P3 베이스라인과 v0 (40~85분)
1. 기존안을 같은 지표로 먼저 채점(`$baseline-and-verify`). 없으면 단순 규칙 해.
2. 끝까지 한 번 도는 가장 작은 흐름 하나만 구현. 스택은 `$dart-web-stack`(Jaspr 기본, Serverpod는 환경 점검 통과 시), 계산은 `$optimization-modeling`, 화면은 `$web-design`.
3. 단위마다 구현 → 직접 검증 2가지(`VERIFY.md`) → 로컬 커밋.
4. 빨간 펜 메시지: 결론 한 줄 + 기존안 대비 숫자 2개 + 확인받을 질문 2개(가장 자신 없는 가정, 현업이 보면 이상할 지점).
- 게이트: 서버 실행 + `/api/health` 200 + 화면 수치 = API 수치 + 메시지 발송.

### P4 빨간 펜 반영, 시나리오, 종적 연결 (85~130분)
1. 피드백 반영. 요구가 바뀌면 이유를 묻는 한 줄과 우리가 먼저 내는 다음 안을 같이 쓴다.
2. 관점이 충돌하면 시나리오 2~3개(예: 이용자 우선 / 비용 우선 / 균형). 파라미터는 화면에서 조절.
3. 종적 연결: 화면 맨 위에 결정권자용 결론 한 줄, 그 아래 기존안 대비 비교표, 그 아래 실무 결과(배정표, 시간표). 실무 → 보고 → 의사결정이 한 화면에서 이어지게.
4. 화면 다듬기는 `frontend-design` 또는 `impeccable`의 점검 항목만 짧게. 새 기능 추가 금지.
- 게이트: 시나리오 비교가 화면에 보이고 수치 검증 통과.

### P5 검토와 운영 위험 (130~150분)
1. 코드를 고치지 말고 빠진 것, 틀린 것, 보안, 운영 위험을 표로. 사용자가 고친다고 고른 것만 고친다.
2. 잘못된 입력, 규칙 변경, 데이터 교체, 개인정보를 `DECISIONS.md` 리스크 표에.
- 게이트: 사용자가 고칠 항목 선택 완료.

### P6 인계와 제출 (150~180분)
1. `RESULT.md`: 결론, 기존안 대비 숫자, 선택한 시나리오와 이유, 버린 것, **운영 인계**(메인테이너, 기준을 바꾸는 위치, 데이터 교체 방법, 재계산과 검증 명령).
2. `HANDOFF.md` 갱신(`$handoff`), `$cognition-prep`으로 서술형 브리프.
3. 최종 메시지: 두괄식 5줄. 결론, 숫자, 남은 위험 하나, 다음에 할 일 하나, 운영 방법 위치.
4. 170분에 제출 시작. push 금지, 로컬 커밋까지.

## 출력 형식 (매번 이것만)
```
[P2 합의] 경과 27분 / 남은 153분 / 단계 예산 13분 남음

한 일
- (2~4줄, 만든 파일 이름 포함)

담당자에게 보낼 메시지 (복붙)
> ...(6줄 이하, 두괄식)

내가 정할 것 (하나)
- 질문: ...  내 추천: ...  이유 한 줄: ...
  (답하면 DECISIONS.md "사람 결정"에 남김)

다음 명령
- 메시지 보낸 뒤 답이 오면: $fde-pilot 답장 <붙여넣기>
```
- "내가 정할 것"은 사용자가 이유를 말할 수 있어야 하는 판단으로 고른다(인지 축). 사용자의 답과 이유를 그대로 `DECISIONS.md`에 기록한다.
- 메시지는 긴 AI 문체 금지(워크슬롭). 사람의 판단이 담긴 짧은 글. em dash를 쓰지 않는다.
- 단계마다 끝나면 로컬 커밋(`git commit -m "P2: 합의안 작성"`).
